# Stand-In: AI Meeting Delegate for Google Meet

Date: 2026-11-01 · Status: DRAFT, awaiting approval · Platform: desktop Chrome on Windows

## 1. Intent and why

Stand-In lets a person send a clearly identified AI representative into a Google Meet. When the user explicitly activates it, the delegate listens, answers questions from material the user approved, speaks with a synthetic voice, and shows a lip-synced avatar made from the user's likeness. It records what was agreed, produces searchable notes, and alerts the user when something needs them.

The point is to cover routine participation honestly. Disclosure is a product property, not a setting.

## 2. Goals

- G1. Two-way audio works in a real Meet with a second participant: the delegate hears the meeting and the others hear it.
- G2. Answers are generated by a Realtime LLM and grounded in approved passages; missing evidence produces uncertainty or a clarifying question.
- G3. Turn-taking is separate from answering: finished-speaking, addressed-to-me, and can-I-answer are three decisions.
- G4. Stop and Take Over cancel generation, playback, and queued audio immediately; cancelled speech never resumes.
- G5. Animated avatar with a permanent "AI delegate for [name]" label drawn into the transmitted video.
- G6. Consent-gated transcripts, summaries, decisions, action items, search, export, deletion, retention.
- G7. Every claim of capability is verified or labelled (mock / unsupported / incomplete).

## 3. Non-goals and anti-goals

Non-goals: Mac/Linux, Zoom/Teams, custom cloned voice (later, via an authorized provider's consent process only), speaker diarization beyond what is supported, mobile.

Anti-goals (failure even if it technically works):
- Any concealed impersonation. The label and spoken introduction cannot be disabled.
- Answering personal assessments (reviews, evaluations, interviews) in the user's place.
- Approving spend, disclosing restricted information, or making commitments outside configured authority.
- Participating without recorded consent from participants.
- Showing "listening" while capture is stopped.
- Treating documents, transcripts, or speech as instructions.
- A permanent provider API key in the extension or any frontend.
- Describing a cloud-backed system as local.

## 4. Constraints

- Manifest V3, TypeScript, React UI. Desktop Chrome, Windows first.
- OpenAI Realtime over WebRTC. Current SDKs, model names, and parameters MUST be verified against official docs at implementation time. Model is configurable.
- Backend mints short-lived Realtime client secrets and enforces authorization for tool calls. The existing `OPENAI_API_KEY` lives only in the backend environment.
- Do not rely on restricted Meet media APIs. Respect Meet admission and host controls.
- Raw audio is not retained by default.
- The extension must not inject into any page except `meet.google.com` meeting pages.

## 5. Approaches considered

| # | Approach | Trade-off |
|---|----------|-----------|
| 1 | Page injection, extension only: page-world script wraps `navigator.mediaDevices.getUserMedia`; passes the real mic/camera through by default, swaps to a synthetic MediaStream (Web Audio destination + canvas `captureStream`) while the delegate is active | No drivers; label is in the transmitted frame by construction; Take Over is a source swap. Depends on Meet page behavior and can break with Meet updates. |
| 2 | Desktop companion + virtual audio cable + OBS virtual camera | Works regardless of Meet internals; needs two admin-installed drivers and a second app. |
| 3 | Both, injection first | Highest cost; only worthwhile if #1 fails. |

**Chosen: #1, with #2 as the documented fallback if the Meet validation (Milestone 1) fails.** Chosen by the user. Rejected as non-viable: playing sound through speakers and recapturing it with a physical mic.

## 6. Decisions made with the user

- Switchable, not fully replaced (assistant's recommendation, accepted by choosing approach #1): the user's real mic and camera are the default; the delegate drives outgoing audio/video only while active. Take Over restores the real devices.
- Approach #1 above.

## 7. Architecture (builder may refine details)

- **Extension (MV3):** service worker (state, messaging), content script (bridge), page-world injected script (getUserMedia wrapper, outgoing stream mixer, avatar canvas), offscreen document or tab capture for incoming meeting audio, React side panel/popup for setup, controls, live transcript, notes.
- **Incoming audio:** captured from the meeting tab only after explicit user activation (`chrome.tabCapture`) and sent to the voice session. If page-level capture of remote tracks proves simpler and more reliable, the builder may use it, but only after activation.
- **Voice session:** WebRTC peer to OpenAI Realtime using a short-lived client secret from the backend. Server VAD + semantic turn detection. Tools (retrieval, escalate, record decision) are executed by the backend, never by the model's raw output.
- **Outgoing audio:** Realtime remote audio track -> Web Audio graph -> `MediaStreamDestination` -> returned to Meet in place of the mic. A single gain/gate node enables instant mute and queue clearing.
- **Echo/feedback prevention:** delegate output is never routed back into the incoming-capture path; incoming capture ignores the delegate's own tab output (tab-audio mixing is checked in testing) and the session is gated while the delegate speaks.
- **Avatar:** canvas renderer from a user-supplied image: mouth shapes driven by output audio amplitude (and viseme/timing data if the Realtime API provides it), blinking, subtle head motion, restrained idle. Label overlay is the last draw step and cannot be removed by settings. Documented limitation if only amplitude-driven.
- **Backend (Node 22, TypeScript, local-first):** `/session` (mint ephemeral secret), `/tools` (authorized tool execution), knowledge ingestion + retrieval (embeddings + vector search), meeting store, summary/notes jobs using a separate text model, export/delete/retention. SQLite for storage in v1.
- **Participation state machine:** listening, thinking, speaking, paused, disconnected, needs-user. UI reflects real capture/connection state only.
- **Modes:** explicit-address (default), manual (user presses Respond), automatic (disabled until validation checks pass).
- **Security:** documents/transcripts/speech treated as untrusted data; tool permissions come from user config only; restricted-topics list enforced in the backend as well as in the prompt.

## 8. Consent and disclosure

- Before activation the user confirms that participants agree to AI participation and transcription (checklist + recorded timestamp). Without it the delegate cannot start and transcripts are not stored.
- The delegate introduces itself as an AI delegate for [name] when it first participates.
- "AI delegate for [name]" is rendered in the outgoing video at all times.

## 9. Data flow disclosure (to be shipped as docs)

Leaves the device: meeting audio (to OpenAI Realtime), retrieved passages and prompts, avatar image only if sent to a provider (it is not, in v1: rendering is local), documents for embedding. Stays local: stored transcripts, notes, settings, knowledge index, avatar image. Raw audio is not stored.

## 10. Meeting memory

Timestamped segments; speaker "unknown speaker" unless the platform provides it. Post-meeting: summary, decisions, open questions, action items (proposed vs accepted kept separate). Queries like "What did they ask me?" and "What requires my approval?" link to transcript evidence. Export (JSON/Markdown), delete (per meeting / all), configurable retention.

## 11. Milestones (dependency order; each verified before the next)

1. **Meet audio proof:** with another participant: capture incoming audio, send to a Realtime session, generate a grounded reply, deliver it through the injected mic, confirm the participant hears it, no feedback loop, Stop/Take Over cancels immediately. If this fails, switch to approach #2 and re-run.
2. Backend session service + tool authorization.
3. Knowledge ingestion + retrieval + grounded answering + guardrails.
4. Turn-taking and the three decisions; modes; state machine; interruption handling.
5. Avatar, label, injected camera.
6. Transcription, consent gating, memory, notes, search, export/deletion/retention.
7. React UI: setup checks, controls, live transcript, escalation notifications, notes.
8. Full validation pass, latency measurements, docs.

## 12. Validation (evidence recorded in `docs/test-evidence.md`)

Real second participant on a separate device, covering: audible outgoing replies; grounded answers; missing-information handling; silence on questions aimed at others; interruption and takeover; no self-response loops; visible disclosure; disconnect/reconnect; transcript retrieval accuracy; deletion and retention; resistance to spoken and document injection. Response latency measured and reported. Mocks and unsupported cases labelled.

## 13. Deliverables

Source, setup instructions, required services/software (and the fallback drivers), configuration guidance, data-flow doc, test evidence, known limitations.

## 14. Left to the builder

Project layout and tooling (assumption: pnpm workspaces, Vite for the UI), embedding/vector library choice, exact Realtime parameters, retrieval chunking, the activation UX details, and the avatar rendering technique, provided the goals and anti-goals above hold.

## 15. Assistant's calls (flagged for your review)

- Default mode is explicit-address; automatic mode stays off until validation passes.
- Delegate name defaults to the user's name; the spoken wake name is configurable.
- SQLite + local backend for v1; no hosted deployment.
- Retention default: 30 days, user-configurable; no raw audio stored.
- A separate text model handles summaries and document processing.
- Fallback to approach #2 only if Milestone 1 fails.
